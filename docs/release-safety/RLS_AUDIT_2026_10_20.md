# RLS / permission audit — October 20, 2026

Scope: every table created in `supabase/migrations/` (frozen) and journaled
`drizzle/migrations/` (182 public tables), with focus on the professional layer and
intelligence workbench (0058–0094). Source-level audit only: **no production catalog was
queried for this report.** Live policies can differ from source (see the 0082/0090/0092
ledger collisions and pending 0058–0078); run the read-only queries at the end of
`0096_rls_hardening.candidate.sql` against the target before relying on it.

## Method

1. Parsed every `CREATE TABLE`, `ENABLE ROW LEVEL SECURITY`, `CREATE/DROP POLICY`,
   `GRANT/REVOKE` across both histories in journal order (final state after drops).
2. Manually re-checked every table the parser reported with zero policies or broad grants,
   including grants/revokes inside `DO` blocks (e.g. 0079 revokes the demo seed tables).
3. Checked every `SECURITY DEFINER` function for a caller check (`auth.uid()`/admin) or an
   EXECUTE revoke from `PUBLIC`/`anon`, per `docs/MIGRATIONS.md`.
4. Reproduced each finding in disposable PGlite on the full journaled schema
   (`scripts/migration-checks/rls-hardening-candidate.check.mjs`).

## Result summary

- **RLS disabled:** none. Every public table in source has RLS enabled.
- **`USING (true)` policies remaining:** none (the demo `USING (true)` policies were dropped
  in 0079).
- **Deny-all by design (RLS on, no client policy, client grants revoked):** 19 tables —
  service-role only: `capability_usage`, `intro_request_nudges`, `account_deletions`,
  `app_settings`, `member_activation`, `member_activity_days`, `agent_rate_counters`,
  `agent_inbound_hashes`, `companies`, `signals`, `seed_threads`, `seed_learnings`;
  RPC-only: `private_library_records`, `private_library_enrichment_suggestions` (0066
  export denial), `professional_opportunities`, `professional_opportunity_saves`,
  `professional_opportunity_interests` (0090), `member_tiers`, `executive_applications`
  (0092). These are correct and must **not** receive permissive policies. The candidate
  adds catalog comments so the intent is visible.
- **Intentionally public:** `impact_reports` (`anon` reads `published` rows only).

## Findings and fixes

| # | Severity | Finding | Fix |
| --- | --- | --- | --- |
| 1 | High | `public.is_approved_member(uuid)` (recorded from live in 0029) is `SECURITY DEFINER`, takes any user id, has no caller check and keeps the default `PUBLIC` EXECUTE: anyone with the anon key can test whether a user id is an approved member. Reproduced in PGlite. | Candidate 0096 §1: revoke from `PUBLIC, anon`; keep `authenticated`, `service_role`. Verified member policies/RPCs that call it still work. |
| 2 | Medium | `outcome_reactions` (0070, intelligence/reputation): INSERT requires a visible outcome by someone else, but UPDATE only checks `reactor_id` and the table has full UPDATE grant, so a member can re-point a reaction to **their own** outcome (self-endorsement into reputation) and backdate `created_at`. Reproduced. | Candidate 0096 §2: guard freezes `outcome_id`/`created_at` on update; UPDATE `WITH CHECK` mirrors INSERT. Existing `reactToOutcome` upsert path verified unchanged. |
| 3 | High (known) | General `save_workspace_state` (SECURITY DEFINER, 0047) can bypass the 0094 ICP guard once `icp:` keys are allowed by the key CHECK. | Already proposed in `icp-reconciliation.proposed.sql` (unapplied). Not duplicated. |
| 4 | Info | 0058–0078 policies (deal rooms/workspaces, private library, briefs, track record, reputation, referrals, analyst, storefronts, syndication, peer-group agendas) are owner/participant scoped (`auth.uid()`), writes go through guarded RPCs where no client write policy exists. They are **not live** (pending recovery), so the professional-layer UI depending on them cannot work in production yet. | Recovery order in `MIGRATION_NORMALIZATION_2026_10_20.md`. |

No table needed a brand-new client policy: every table without one is deliberately
RPC/service-role only, and adding `auth.uid()` policies to them would widen access
(e.g. bypass the 0066 contact export denial). "Add missing policies" was therefore
satisfied by verifying intent and documenting it, not by adding permissive policies.
